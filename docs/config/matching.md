# ⚖️ 匹配裁决层（Arbiter）

决定「搜索到的一堆候选里，到底采用哪一个、够不够格自动采用」。

默认**关闭**，行为与此前完全一致。开启后改为「双阈值」判定：既看**分数够不够**，也看**领先第二名多少**。

## 解决什么问题

关闭状态下只有一个阈值（`[sync] match_confidence_threshold`，默认 `0.6`）：只看选中条目的相似度分数，分数够就自动标记。

这带来两个问题：

1. **「够格」只有一把尺子**。两个候选分别是 0.90 和 0.88 时，其实分不出谁对，但仍会采用第一名 —— 这类「险胜」是静默标错的主要来源。
2. **分数≠可信度**。相似度只说明标题像，不说明它在候选里是否真的突出。

开启裁决层后，判定变成：

| 判定 | 含义 | 结果 |
| --- | --- | --- |
| 加权分 < `min_score` | 不够格 | 沉淀待审 |
| 领先第二名 < `ambiguous_margin` | 条目本身有歧义 | 沉淀待审 + 歧义通知 |
| 领先第二名 < `min_margin` | 险胜，不足以自动采用 | 沉淀待审 |
| 其余 | 分数够且明显领先 | 自动采用 |

## 配置项

Web「配置管理」→「匹配裁决层」卡片，对应 `config.ini` 的 `[matching]` 段。

| 配置项 | 默认值 | 说明 |
| --- | --- | --- |
| **启用裁决层** | 关闭 | 总开关。关闭时沿用 `[sync] match_confidence_threshold` 单阈值判定 |
| **最低加权分** | `0.85` | 低于此值判定为无匹配。调研实测 `0.6` 时精确率仅 92.6% |
| **最低领先幅度** | `0.10` | 与第二名分差小于此值时沉淀待审 |
| **歧义阈值** | `0.05` | 分差小于此值视为条目本身有歧义，额外发送歧义通知 |
| **各来源权重** | 均为 `1.0` | 见下方「来源权重」 |

### 来源权重

同一条目可能被多个来源（本地归档 / API 搜索 / bangumi-data / 自定义映射）同时命中。裁决时按 `max(权重 × 分数)` 取值 —— **让最可信的来源主导判定**，而不是把各来源分数平均（平均会让低分来源稀释高分来源）。

权重调低某个来源，等于降低它的发言权。例如把 `weight_archive` 设为 `0.5`，则归档候选需要比 API 候选高出一大截才能胜出。

## 实测效果

在 240 条真实归档用例上对比（脚本：`.workbuddy/research/matching-pipeline/eval_arbiter.py`）：

| 指标 | 关闭（现状） | 开启（裁决） | 变化 |
| --- | --- | --- | --- |
| 自动采用数 | 222 | 206 | −16 |
| 覆盖率 | 92.5% | 85.8% | −6.7% |
| **精确率** | 95.9% | **99.0%** | **+3.1%** |
| **错命中数** | 9 | **2** | **−7** |
| 沉淀待审数 | 18 | 34 | +16 |

也就是说：**拦下 7 条错误标记的代价，是把 9 条原本正确的匹配转为待人工确认**。

是否划算取决于你的偏好：

- 若**静默标错**更难受（标到了错误的番剧，看起来一切正常），建议开启
- 若**少标**更难受（宁可自动标上，错了再改），保持关闭

## 注意事项

- 裁决层**只做「是否采用」的门控，不会推翻季度 / 媒体类型 / 关联条目的改选结果**。改选是领域逻辑（例如搜索命中第二季但实际应标第一季），不是分数比较，用加权分推翻它会误伤。
- 被沉淀的条目可以在 Web 界面的待审队列里手工确认，不会丢失。
- 调低 `min_score` 可以提高覆盖率，但会同时放更多错误匹配通过；调整后建议先在少量数据上观察。
